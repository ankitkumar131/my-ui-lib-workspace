Foundation Rules — Angular UI Component Library (the source of truth)

These are the working rules for this repository. They describe how the codebase is actually organized today; contributors should follow them and propose rule changes via PR when conventions evolve.

Purpose & scope

Build a reusable, production-grade Angular UI component library (consumer package + demo app) modeled on modern design systems (shadcn/Radix-style composition, original implementation).

Ship small, focused components (ui-button, ui-card, ui-badge, …) that are accessible, themeable, responsive, performant, and well-documented.

Core principles (always)

Stable & supported APIs — No deprecated Angular/TS/DOM APIs. If something is deprecated, replace before merging.

Minimal public surface — Each component folder exposes a public-api.ts; export only what consumers need. Keep internal helpers private.

Accessibility first — Keyboard + screen reader support is required for interactive components (focusable triggers, Escape/arrow handling where applicable, ARIA only when native semantics are insufficient).

Design tokens & theming — All colors come from projects/my-ui/styles/_tokens.scss (--ui-* custom properties). Components never hard-code palette colors and never define their own dark-mode media blocks; dark mode is handled once in the token file.

Small bundles & tree-shaking — Every component is a published secondary entry point (@my-ui/components/<name>) so deep imports stay small. Avoid side-effectful top-level code.

Mobile-first responsive design — Use the respond() mixin from styles/_mixins.scss at the breakpoints listed below.

Predictable naming — Component element selectors use the ui- prefix (kebab-case). CSS classes use ui-<component> (or a compact component-class like .button-container) with __ / -- BEM-style parts where useful.

Repository layout (actual)

my-ui-lib-workspace/            (Angular CLI multi-project workspace)
├─ src/                          demo app (component playground)
├─ projects/my-ui/               @my-ui/components — the library
│  ├─ <component>/               one folder per component, e.g. button/
│  │  ├─ ng-package.json         secondary entry point (entryFile: public-api.ts)
│  │  ├─ public-api.ts           canonical exports (raw + alias names)
│  │  ├─ index.ts                re-exports public-api.ts (source-map convenience)
│  │  ├─ <component>.module.ts   optional NgModule wrapper (components are standalone)
│  │  ├─ components/<part>/      part.component.ts / .html / .scss
│  │  ├─ directives/ services/ types/  as needed
│  │  └─ <Component>_Manual.md   usage manual (legacy docs, kept up to date)
│  └─ styles/                    _tokens.scss, _mixins.scss (shipped in the package)
├─ scripts/                      one-off maintenance scripts
└─ .github/workflows/ci.yml      lint -> test -> build pipeline

Naming & file conventions

Component element selectors: ui-<name> (kebab-case). Example: ui-button, ui-card.
Attribute directives: ui<Name> camelCase, e.g. uiDropdownMenuTrigger, uiCollapsibleTrigger.
Component classes: ButtonComponent, SelectTriggerComponent. Where shadcn parity is useful, public-api.ts also exports an alias (ButtonComponent as Button).
Modules (legacy wrappers): Ui<Button|Card>Module. New components are standalone — no module needed.
Files: button.component.ts, button.component.html, button.component.scss; types in *.types.ts or *-type.enum.ts.
Public exports: everything a consumer may import goes in the component's public-api.ts (and thus the root public-api.ts re-export).

Imports & entry points

Inside the workspace, always import via package aliases (tsconfig paths):
  @my-ui/components          → root entry (all components)
  @my-ui/components/button   → secondary entry (tree-shakeable)
Never use relative imports across component folders; secondary entry points must import each other by package name only (required by ng-packagr).

SCSS & styling rules (enforced)

All palette/semantic colors come from _tokens.scss (--ui-background, --ui-foreground, --ui-card, --ui-popover, --ui-muted, --ui-muted-foreground, --ui-border, --ui-accent, --ui-brand, --ui-focus, --ui-destructive, --ui-selection, …). Component CSS references tokens, e.g. var(--select-trigger-bg, var(--ui-popover)).
No prefers-color-scheme blocks in component stylesheets — dark mode lives exclusively in _tokens.scss.
Prefer px for spacing/sizing; rem is acceptable for typography and radii. Never introduce other units ad hoc.
No inline styles in templates and no SCSS/HTML inside .ts files. Use separate .html/.scss files.
Scoped styles only: use :host and component class prefixes. ::ng-deep only where child-element projection requires it (existing pattern in button/button-group) — prefer avoiding it in new code.
Avoid !important. Avoid global selectors that can clash with consumer apps.
Component-level CSS vars keep their --<component>-* names as the public override API (e.g. --select-trigger-height, --dropdown-item-hover-bg). Defaults must resolve to shared tokens.
color-mix() is allowed for derived shades (hover/active states).

Theming & design tokens

Single source of truth: projects/my-ui/styles/_tokens.scss (light + dark via prefers-color-scheme, emitted at :root by the ui-theme mixin).
Consumers add to their global stylesheet:
  @use '@my-ui/components/styles/tokens' as ui-tokens;
  @include ui-tokens.ui-theme;
Consumers override any token (e.g. :root { --ui-brand: #7c3aed; }) or any component var (e.g. .ui-select-trigger { --select-trigger-height: 48px; }).
Adding a color? Add/extend a token first, then use var(--ui-*) in the component.

Breakpoints & responsive targets (canonical)

mobile-s 320px, mobile-m 375px, mobile-l 425px, tablet 768px, laptop 1024px, laptop-l 1440px, 4k 2560px.
Use @include respond(tablet) { … } from styles/_mixins.scss.

Accessibility (A11Y)

Interactive components must be keyboard operable (Tab, Enter/Space, Escape, arrow keys where applicable) — see existing handlers in menus, dialogs, combobox.
Use ARIA only when native semantics are insufficient; keep aria-expanded/aria-checked/role in sync with component state.
Never remove focus outlines without a replacement focus-visible style.

Animations & motion

CSS transitions/animations, 120–300ms. Respect prefers-reduced-motion where motion is essential.

Performance & change detection

Prefer ChangeDetectionStrategy.OnPush for new components (not yet retrofitted across the library — do not add default-CD components).
Avoid deep ngFor without trackBy; lazy-load heavy resources.

Testing & quality gates

Unit tests (Karma + Jasmine) per component, colocated as *.spec.ts next to the component. Interactive components (select, combobox, menus, calendar) must keep coverage as they evolve.
Run locally: npm test (watch) or npm run test:ci (ChromeHeadless, used in CI).
Lint must pass: npm run lint (ESLint flat config; selectors, no-explicit-any, no-unused-vars enforced).
Format before committing: npm run format (Prettier, 100 cols, single quotes).

CI pipeline (.github/workflows/ci.yml)

Runs on pushes/PRs to master: lint → test:ci → build:lib → build. PRs are expected to keep all four green.

Packaging & distribution

Library builds with ng-packagr (npm run build:lib → dist/my-ui). Package name @my-ui/components with one secondary entry point per component folder.
Library package.json declares peerDependencies only (@angular/common, core, forms, cdk, rxjs) — never bundles Angular.
Consume deep imports for smaller bundles: import { Button } from '@my-ui/components/button'.

Versioning & release process

Semantic Versioning. Conventional commit messages (fix:, feat:, chore:, refactor: …).
Release flow: PR → review → CI green → manual publish of dist/my-ui. Tag releases and update the changelog.

Documentation & demos

Every component keeps a demo section in src/app/app.html and a <Component>_Manual.md in its folder; update both when the public API changes.
Document the component's CSS variable override API in the manual.

Security & dependencies

Minimal external dependencies (Angular + CDK only). SVG icons over icon fonts. npm audit before releases.

Quick enforcement checklist (PR template)

 Lint passes (npm run lint)
 Tests pass (npm run test:ci), specs added for changed behavior
 build:lib and build succeed
 No hard-coded palette colors; no new dark-mode blocks (tokens only)
 No any in public APIs; selectors follow ui- prefix
 Accessibility checked (keyboard + ARIA state)
 Docs/manual/demo updated
